# 14. Performance Troubleshooting and Interview Questions

Three questions come up in almost every Linux administrator interview.

## Q1. What Is Your Daily Routine as a System Administrator?

Answer with a concrete picture of your environment and duties. A sample answer:

- I worked as a system administrator at a company running **25 servers**: application servers, database servers and a monitoring server. We were a team of two admins, and I reported to the senior admin.
- Work came in through **ticketing tools** such as Jira, OTRS, ServiceNow and BMC Remedy.

Typical daily duties:

1. **Monitoring** the servers with Nagios or Zabbix.
2. **Storage:** creating partitions and mount points with fdisk for application teams, and extending or reducing space with **LVM**.
3. **Packages:** installing, removing and upgrading software, and **patching**.
4. **Housekeeping:** archiving old data with tar and zip, and cleaning up logs.
5. **Backups:** to tape drives and backup servers.
6. **Permissions:** granting rights on application folders as requested.
7. **Services:** maintaining NFS, Samba, DHCP and FTP.
8. **Logs:** checking `/var/log` and `journalctl`.
9. **Incidents:** when a machine crashed, recovering it (rebooting if needed) and troubleshooting the cause.

## Q2. A Server Is Overloaded. How Do You Diagnose It?

Work from the most common cause to the least.

**Step 1: CPU, memory and swap.** Run `top` (and `free -m`). If CPU, memory or swap is exhausted, find the process using it (sort with `P` for CPU, `M` for memory), and **engage the team that owns the application** to fix or restart it.

**Step 2: Disk.** If no process stands out, check the disks with `iostat -x 2` (look at `%util` and `await`) and the `wa` value in `top`. A saturated or failing disk goes to the storage team or vendor; RAID or faster storage may be the answer.

**Step 3: Network.** If the disks are fine, check the network with `sar -n DEV`, `nmon`, `iperf3`, `tcpdump` or Wireshark for saturation, errors or unusual traffic.

**Step 4: Memory caches.** Linux uses free RAM as **cache** (copies of file data read from disk) and **buffers** (block-device and metadata I/O). Both live in RAM and are released automatically when applications need memory, so high buff/cache is normal. If you must free them, for example before a benchmark:

```bash
sync; echo 3 > /proc/sys/vm/drop_caches
```

Growing memory use by one process that never comes back down is a **memory leak**: a bug for the developers, who find it with tools like **valgrind**.

**Step 5: Hardware.** If all else looks normal, suspect the hardware: test RAM with **memtest86+**, check CPU temperature and throttling (overheating or overclocking), and read the hardware logs (`dmesg`, `journalctl -k`, the vendor's management console).

## Q3. What Critical Problem Did You Face in the Last Month?

Prepare one real story and tell it with the **STAR** method:

| Step | Say |
|---|---|
| **Situation** | The context: which system, what broke, the business impact |
| **Task** | What you were responsible for |
| **Action** | What you checked and changed, in order, with the commands or tools |
| **Result** | The outcome, and what you changed so it won't happen again |

Example topics: a full file system stopping an application (fixed with `lvextend`), a server that wouldn't boot after an fstab mistake (fixed from rescue mode), or a failed patch rolled back with `dnf history undo`.
