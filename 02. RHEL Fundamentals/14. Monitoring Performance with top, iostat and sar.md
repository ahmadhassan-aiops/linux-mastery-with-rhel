# 14. Monitoring Performance with top, iostat and sar

## top

`top` is the Linux task manager: a live view of load, CPU, memory and the busiest processes. It reads everything from `/proc`, the kernel's view of RAM.

### The Summary Lines

| Line | Shows |
|---|---|
| 1 `top` | Current time, uptime, number of logged-in users, and the **load average** over the last 1, 5 and 15 minutes |
| 2 `Tasks` | Total processes and how many are running, sleeping, stopped and zombie |
| 3 `%Cpu(s)` | How CPU time is being spent (below) |
| 4 `MiB Mem` | Total, free, used and buff/cache RAM |
| 5 `MiB Swap` | Total, free and used swap, and **available** memory |

**Load average** is the number of processes running or waiting for the CPU (and, on Linux, waiting for disk). Compare it with the number of CPU cores (`nproc`): a load of 4 on a 4-core server means fully busy.

### The CPU Line

| Field | Time spent on |
|---|---|
| `us` | User processes (applications) |
| `sy` | The kernel (system calls) |
| `ni` | Processes with a changed nice value |
| `id` | **Idle**: nothing to do. Low `id` means the CPU is busy |
| `wa` | **Waiting for I/O** (disk or network). High `wa` points to a storage problem |
| `hi` / `si` | Hardware / software interrupts |
| `st` | **Steal**: time the hypervisor gave to other virtual machines. High `st` on a cloud VM means noisy neighbours or too small an instance |

### Keys Inside top

| Key | Action |
|---|---|
| `P` | Sort by CPU |
| `M` | Sort by memory |
| `u` | Show one user's processes |
| `k` | Kill a process (asks for the PID) |
| `r` | Renice a process |
| `c` | Show the full command line |
| `z` | Colour mode |
| `1` | One line per CPU core |
| `q` | Quit |

Save a snapshot to a file (batch mode, one iteration):

```bash
top -b -n1 > /tmp/top-snapshot.txt
```

`htop` is a friendlier, colourful version (install it from EPEL). More reading: https://www.binarytides.com/linux-top-command/

## Memory: free

```bash
free -m      # in MiB
free -h      # human readable
```

Linux uses spare RAM as **cache** for files, so "free" is often small. Look at the **available** column: that is what applications can still get.

## Disk Load: iostat

`iostat` (package `sysstat`) shows how busy each disk is. Watch `%util`: close to 100% means the disk is saturated.

```bash
iostat -x            # extended statistics for every device
iostat -x -p sda 2 3 # sda and its partitions, every 2 seconds, 3 times
iostat -x 2          # every 2 seconds until Ctrl+C
```

## History: sar

`sar` (System Activity Reporter, also in `sysstat`) records CPU, memory, disk and network statistics every 10 minutes, so you can see what happened at 3 a.m.

```bash
dnf install sysstat
systemctl enable --now sysstat    # start collecting
sar -u                            # today's CPU usage
sar -r                            # memory
sar -d                            # disks
sar -n DEV                        # network interfaces
sar -u -f /var/log/sa/sa15        # CPU on the 15th of the month
```

Reports are stored in `/var/log/sa/`.

## More Monitoring Tools

| Tool | Shows |
|---|---|
| `vmstat 2` | CPU, memory, swap, I/O and context switches every 2 seconds |
| `mpstat -P ALL` | Per-CPU statistics |
| `pidstat` | Live statistics per process |
| `nmon` | An interactive dashboard of everything |
| `iperf3` | Network bandwidth between two machines |
| `tcpdump` | Captures network packets |
| `strace df -h` | Every system call a command makes |
| `pmap -d 1234` | The memory map of a process |
| `ipcs` | Shared memory, semaphores and message queues |
| `lscpu`, `cat /proc/cpuinfo` | CPU details |
| `cat /proc/meminfo` | Detailed memory information |
| `lsusb`, `lspci` | USB and PCI devices |

## Questions

1. `top` shows `id` at 85% but users complain the server is slow, and `wa` is 12%. Where do you look next?
2. A 2-core VM shows a load average of `6.0, 5.8, 5.5`. Is that a problem?
3. How do you check yesterday afternoon's CPU usage?

<details>
<summary>Answers</summary>

1. Disk I/O: `iostat -x 2` to find the saturated device, then `iotop` or `pidstat -d` to find the process.
2. Yes: about three times more work than the CPUs can handle, for at least 15 minutes.
3. `sar -u -f /var/log/sa/saDD` with yesterday's day of the month (add `-s 12:00:00 -e 18:00:00` to limit the time).
</details>
