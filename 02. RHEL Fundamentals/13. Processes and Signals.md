# 13. Processes and Signals

A **process** is a running program. Every process has:

- a **PID** (process ID), a unique number
- a **PPID** (parent process ID): the process that started it

**PID 1** is `systemd` (on RHEL 6: `init`), the first process the kernel starts and the ancestor of all others. PID 0 is the kernel's own idle task and never shows in process lists. Other PIDs are assigned in sequence as processes start, so most change after every reboot.

## Listing Processes

```bash
ps                         # processes in this terminal
ps -ef                     # every process, full format (UID, PID, PPID, start time, command)
ps aux                     # every process, BSD style (with %CPU and %MEM)
ps -el                     # long format, including the state and priority
ps -eo pid,ppid,user,cmd   # choose the columns
ps -eo pid,lstart,cmd      # with the exact start time
ps -ef | grep -i httpd     # find a particular process
pidof sshd                 # PID(s) of a program by name
pgrep -l ssh               # PIDs matching a pattern
pstree -p                  # the whole process tree with PIDs
echo $$                    # the PID of your current shell
lsof                       # every open file and the process using it
lsof -p 1234               # files opened by PID 1234
```

## Process States

| State | Meaning |
|---|---|
| `R` | **Running** or ready to run on a CPU |
| `S` | **Sleeping**: waiting for an event (most processes, most of the time) |
| `D` | **Uninterruptible sleep**: waiting for disk or network I/O; can't be killed until it returns |
| `T` | **Stopped** (paused with Ctrl+Z or a signal) |
| `Z` | **Zombie** (defunct): finished, but its parent hasn't collected its exit status yet |

Zombies use no CPU or memory, only a slot in the process table. They come from buggy parent programs: kill or restart the **parent** and `systemd` cleans them up. Only a huge number of zombies is a real problem.

## Signals and kill

`kill` sends a **signal** to a process.

| Signal | Number | Effect |
|---|---|---|
| `SIGTERM` | 15 | Polite request to stop (the default). The program can clean up |
| `SIGKILL` | 9 | Immediate, forced stop. Can't be caught or ignored |
| `SIGHUP` | 1 | Hang up; many daemons reload their configuration |
| `SIGINT` | 2 | Interrupt, the same as Ctrl+C |
| `SIGSTOP` / `SIGCONT` | 19 / 18 | Pause / resume |

```bash
kill 1234            # SIGTERM
kill -15 1234        # the same, explicitly
kill -9 1234         # SIGKILL: use only when SIGTERM fails
kill -1 $(pidof nginx)   # ask nginx to reload
pkill firefox        # by name
killall httpd        # every process with that name
kill -l              # list all signals (64 on Linux)
```

> 💡 Always try `kill` (15) before `kill -9`: SIGKILL gives the program no chance to save data or remove lock files.

PID 1 can't be killed, even with `kill -9`. A runaway user can still hang a machine by starting processes endlessly (a "fork bomb") until the process table and memory are full; per-user limits in `/etc/security/limits.conf` (`nproc`) prevent this.

## Foreground and Background Jobs

```bash
firefox &            # start in the background; the shell stays free
jobs                 # list this shell's background jobs
fg %1                # bring job 1 to the foreground
bg %1                # continue a paused job in the background
Ctrl+Z               # pause the foreground job
nohup ./backup.sh &  # keep running after you log out (output goes to nohup.out)
```

| | Survives closing the terminal? |
|---|---|
| `command &` | No: it ends with the shell |
| `nohup command &` | Yes |
| `systemd` service or `tmux`/`screen` session | Yes, and the best choice for long jobs |

## Priority: nice and renice

The **nice value** sets how much CPU time a process gets compared to others. It ranges from **-20 (highest priority)** to **19 (lowest priority)**; the default is 0.

```bash
nice -n 10 tar czf /backup/home.tgz /home   # start with low priority
renice -n -5 -p 1234                        # raise priority of a running process (root only)
```

In `top`, press `r`, enter the PID and the new nice value. Lowering a long job's priority (for example, a 2-hour copy) keeps the server responsive for everything else; only root can give a process a negative (higher) priority.

## Questions

1. A process ignores `kill 4321`. What do you try next, and what is the risk?
2. How do you find the parent of a zombie process?
3. Start a long script so it keeps running after you disconnect from SSH.

<details>
<summary>Answers</summary>

1. `kill -9 4321`. The process can't clean up, so data in memory or lock files may be left behind.
2. `ps -eo pid,ppid,stat,cmd | grep Z` shows the zombie's PPID, which is its parent.
3. `nohup ./script.sh &` (or run it in `tmux`).
</details>
