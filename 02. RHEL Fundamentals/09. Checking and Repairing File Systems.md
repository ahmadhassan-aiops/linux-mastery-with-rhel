# 09. Checking and Repairing File Systems

## Why File Systems Become Inconsistent

- Unclean shutdown or sudden power loss
- Power fluctuations
- Bad sectors on the disk
- Badly designed applications that leave writes half-finished

Usually it's the **file system metadata** that gets damaged, not the data itself, and the repair tools rebuild that metadata.

## Find Bad Blocks

```bash
badblocks -v /dev/sdb1      # read-only scan for unreadable sectors
```

Bad blocks found? Repair the file system, and plan to replace the disk.

## Repair

**Always unmount first.** Repairing a mounted file system can make things worse.

```bash
umount /tomcat
```

| File system | Check and repair | Notes |
|---|---|---|
| ext2/3/4 | `e2fsck /dev/sdb1` or `fsck /dev/sdb1` | `fsck` detects the type and calls `e2fsck` |
| ext2/3/4, unattended | `e2fsck -y /dev/sdb1` | Answer "yes" to every repair |
| ext2/3/4, with a bad-block scan | `e2fsck -yc /dev/sdb1` | `-c` runs `badblocks` and marks bad sectors |
| xfs | `xfs_repair /dev/sdb1` | The RHEL default file system; `fsck` does nothing on XFS |
| xfs, report only | `xfs_repair -n /dev/sdb1` | No changes |

Then mount it again:

```bash
mount /tomcat     # uses the fstab entry
```

The **root** file system can't be unmounted while the system runs. Repair it from **rescue mode** (boot from the installation ISO, or add `rd.break` / `systemd.unit=rescue.target` at the GRUB menu).

## Automatic Checks at Boot

The 6th field in `/etc/fstab` controls this (topic 08): `0` never checks, `1` checks the root first, `2` checks the other file systems afterwards. XFS ignores it and repairs itself through its journal; ext4 file systems are checked when needed.

## Questions

1. `fsck /dev/sdb1` reports nothing useful on a RHEL 9 data disk. Why?
2. What must you do before running `e2fsck` on `/dev/sdc1`, mounted on `/data`?

<details>
<summary>Answers</summary>

1. The disk is probably XFS: use `xfs_repair` instead.
2. `umount /data` (check with `lsof /data` if it is busy).
</details>
