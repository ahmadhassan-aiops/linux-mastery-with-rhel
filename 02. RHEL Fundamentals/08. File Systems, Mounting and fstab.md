# 08. File Systems, Mounting and fstab

## Formatting Means Creating a File System

A new partition is raw space. **Formatting** creates a **file system** on it: the metadata ("data about data") that records where every file lives, like a book's table of contents.

File system metadata includes:

1. **Inodes:** one per file (permissions, owner, size, timestamps, data location)
2. **The inode table**
3. **Data blocks:** where file contents are stored
4. **The superblock:** the file system's own size, block size and state
5. **Mount information**

> 💡 Formatting rewrites the metadata, not the data itself. That is why deleted or "formatted" data can often be recovered with forensic tools until it is overwritten, and why secure erasure needs tools like `shred` or full-disk encryption.

## Creating a File System

```bash
mkfs.xfs /dev/sdb1      # the RHEL default
mkfs.ext4 /dev/sdb1     # the common alternative
df -Th                  # type and size of mounted file systems
lsblk -f                # file system type and UUID of every partition
```

## Linux File System Types

| File system | Command | Best for | Pros | Cons |
|---|---|---|---|---|
| **ext2** | `mkfs.ext2` | Old systems, small flash drives | Simple, low overhead | No journaling: slow recovery after a crash |
| **ext3** | `mkfs.ext3` | Older general-purpose systems | Journaling, compatible with ext2 | Slower than ext4, limited scalability |
| **ext4** | `mkfs.ext4` | General purpose, the Ubuntu default | Journaling, fast, large files, can **shrink** | Less scalable than XFS for huge volumes |
| **xfs** | `mkfs.xfs` | Large, high-performance file systems; the **RHEL default** | Fast, scales well, efficient allocation | **Cannot shrink** |
| **btrfs** | `mkfs.btrfs` | Snapshots, subvolumes, built-in RAID | Advanced features, self-healing | Not supported by RHEL |
| **vfat (FAT32)** | `mkfs.vfat` | USB sticks shared with any OS | Works everywhere | No journaling, 4 GB file limit |
| **exFAT** | `mkfs.exfat` | Large external drives | Large files, wide compatibility | No journaling |
| **ntfs** | `mkfs.ntfs` | Dual boot with Windows | Windows native | Limited Linux support |
| **swap** | `mkswap` | Swap space | Essential for memory management | Not for files |

**Journaling** means the file system keeps a log of changes before making them, so after a power cut it can recover in seconds instead of checking the whole disk.

### Quick Comparisons

| | |
|---|---|
| **ext2 vs ext3** | ext3 adds journaling, giving fast crash recovery |
| **ext3 vs ext4** | ext4 supports files up to 16 TB (ext3: 2 TB), volumes up to 1 EB, more subdirectories and better performance |
| **ext4 vs xfs** | Both journal. XFS performs better on large files and volumes. ext4 can be shrunk; XFS can only grow. Neither has built-in snapshots on RHEL: use LVM snapshots for both |

## Mounting

A file system is used by **mounting** it on a directory (the **mount point**). The data lives on the partition; the directory is just the door to it.

```bash
mkdir /tomcat
mount /dev/sdb1 /tomcat
df -h                     # /dev/sdb1 now appears on /tomcat
umount /tomcat            # detach it
```

Unmount, mount the same partition on another directory, and you see exactly the same files: only the mapping changed.

A `mount` done by hand is **temporary**: it is lost at the next reboot.

## Persistent Mounting with /etc/fstab

`/etc/fstab` (**file system table**) is read at every boot, which mounts everything listed in it. It is one of the most critical files on the system.

Each line has **6 fields**, separated by spaces or tabs:

```text
UUID=3f1c...e9   /tomcat   xfs   defaults   0 0
  1                 2       3       4       5 6
```

| # | Field | Meaning |
|---|---|---|
| 1 | Device | `/dev/sdb1`, or better a **UUID** (doesn't change if disks are renamed) |
| 2 | Mount point | `/tomcat` |
| 3 | Type | `xfs`, `ext4`, `swap`, `nfs` |
| 4 | Options | `defaults`, or a comma-separated list (below) |
| 5 | Dump | `1` to include in `dump` backups, `0` otherwise (almost always 0) |
| 6 | fsck order | `0` = never check at boot, `1` = check first (the root file system), `2` = check after the root. Disks with the same number are checked in parallel |

Find a partition's UUID:

```bash
blkid /dev/sdb1
lsblk -f
ls -l /dev/disk/by-uuid/
```

**Always test before rebooting:**

```bash
vi /etc/fstab        # add the line
mount -a             # mount everything in fstab that isn't mounted yet
findmnt --verify     # check fstab for errors
df -h
```

> ⚠️ A typo in `/etc/fstab` can stop the server from booting into normal mode. That is why changes to fstab on **production** servers go through change control and are tested on dev, UAT or POC servers first.

| Server type | Purpose |
|---|---|
| **Production (prod)** | Live, serving real users |
| **Development (dev)** | For developers |
| **UAT** | User Acceptance Testing |
| **POC** | Proof of Concept, for demos |

### Mount Options (Field 4)

| Option | Meaning |
|---|---|
| `defaults` | `rw, suid, dev, exec, auto, nouser, async` |
| `ro` / `rw` | Read-only / read-write |
| `auto` / `noauto` | Mount / don't mount with `mount -a` and at boot |
| `exec` / `noexec` | Allow / forbid running programs from it (`noexec` is common on `/tmp`) |
| `user` / `nouser` | Allow / forbid normal users to mount it |
| `suid` / `nosuid` | Honour / ignore SUID bits |
| `async` / `sync` | Buffered / immediate writes |
| `_netdev` | Wait for the network (NFS, iSCSI) |

Combine options with commas: `ro,noexec,nosuid`. When options conflict, the last one wins: `defaults,ro` means read-only.

Changing the options in fstab doesn't affect a file system that is already mounted. Apply the change without unmounting:

```bash
mount -o remount /tomcat
```

## How It Fits Together

When the system starts, the OS is loaded from disk into **RAM**, and the CPU only works on what is in RAM. `mount` loads a file system's metadata into memory, which is why a mounted file system must be unmounted before it is repaired (topic 09).

## Questions

1. You mounted `/dev/sdc1` on `/data`, and after a reboot it's gone. Why, and how do you fix it?
2. Write the fstab line for an ext4 partition with UUID `1234-abcd` on `/backup`, read-only, checked after the root file system.
3. Which file system would you choose for a volume that may need to shrink later?

<details>
<summary>Answers</summary>

1. A manual mount is temporary. Add it to `/etc/fstab` and test with `mount -a`.
2. `UUID=1234-abcd  /backup  ext4  ro  0 2`
3. ext4, since XFS cannot be shrunk.
</details>
