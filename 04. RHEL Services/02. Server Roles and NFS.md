# 02. Server Roles and NFS

## One Service per Server

A single server could run every service (web, database, file sharing, DNS), but in production we don't do that:

- If that one server goes down, **every** service goes down with it.
- Each service gets its own resources, so one busy service doesn't slow the others.

For **high availability**, important servers are also **clustered**: two or more machines with fail-over, so a standby takes over when the active one fails.

## NFS: Network File System

| Fact | Detail |
|---|---|
| Purpose | Share directories from a Linux server so clients mount them like local folders |
| Between | Linux/Unix and Linux/Unix |
| Port | **2049** (plus `rpcbind` on 111, and `mountd` for NFSv3) |
| Transport | **TCP** for NFSv4, the RHEL default; NFSv3 can also use UDP |
| Authentication | By **client host** (IP or network) and by matching user IDs, not with a username and password. Kerberos (`sec=krb5`) adds real authentication |

Compare **Samba** (topic 09): it uses ports 137 to 139 and 445 over TCP and UDP, shares with **Windows** as well as Linux, and asks for a username and password.

## Lab: Share a Directory from server1 to client1

Two RHEL 9 (or CentOS Stream 9) VMs in VirtualBox on the same network.

### 1. Host Names (Both Machines)

```bash
hostnamectl set-hostname server1.example.com    # on the server
hostnamectl set-hostname client1.example.com    # on the client
hostnamectl                                     # check
cat /etc/hostname
```

Without a DNS server, add both machines to **`/etc/hosts`** on both sides (a "flat DNS"):

```text
192.168.56.10   server1.example.com   server1
192.168.56.11   client1.example.com   client1
```

```bash
ping -c 2 server1     # from the client
ping -c 2 client1     # from the server
```

### 2. Install and Start NFS (Server)

```bash
dnf install nfs-utils -y
systemctl enable --now rpcbind nfs-server
ss -tulnp | grep 2049          # NFS is listening
```

### 3. Export a Directory (Server)

```bash
mkdir -p /opt/fileserver
vi /etc/exports
```

```text
/opt/fileserver   192.168.56.0/24(rw,sync)
```

The part in front of the brackets says **which clients** may mount it (a host, a network or `*`), and the options say how:

| Option | Meaning |
|---|---|
| `ro` / `rw` | Read-only / read-write |
| `sync` | Write to disk before replying (safe) |
| `root_squash` | The default: the client's root is treated as the anonymous user `nobody` |
| `no_root_squash` | The client's root stays root on the share (avoid) |

Load the export table into memory, then allow NFS through the firewall:

```bash
exportfs -rv
exportfs -v                     # what is exported now
firewall-cmd --permanent --add-service={nfs,rpc-bind,mountd}
firewall-cmd --reload
```

### 4. Mount on the Client

```bash
dnf install nfs-utils -y
showmount -e server1            # what the server exports
mkdir /myshare
mount server1:/opt/fileserver /myshare
df -h /myshare
```

Files created in `/opt/fileserver` on the server now appear in `/myshare` on the client.

### 5. Mount at Every Boot (Client)

Add to `/etc/fstab`:

```text
server1:/opt/fileserver   /myshare   nfs   defaults,_netdev   0 0
```

`_netdev` makes the boot wait for the network. Test with `mount -a`.

## NFS vs Samba vs FTP

- **NFS** and **Samba** share files: clients work on the files where they live, and lose access if the server goes down.
- **FTP** transfers files: clients download a copy, which they keep even if the server goes down later.

## Questions

2. Write an `/etc/exports` line that shares `/data` read-only with the single host `10.0.0.25`.
