# 08. xinetd and SSH

## xinetd (Legacy)

**xinetd** (extended Internet daemon) was a "super-server": one small daemon that listened on behalf of several rarely used services and started the right one only when a connection arrived, saving memory.

| Service run through xinetd | Notes |
|---|---|
| `telnet` | Remote login, but **unencrypted**: never use it on untrusted networks |
| `tftp` | Trivial FTP over UDP, no login. Used for network (PXE) installations |
| `nrpe` | The agent for the Nagios monitoring tool |
| `amanda` | Network backup |

```bash
# RHEL 6
/etc/init.d/xinetd start
chkconfig xinetd on

# RHEL 7
systemctl enable --now xinetd
```

> ⚠️ xinetd was removed in **RHEL 8**. systemd **socket units** do the same job: for example, `systemctl enable --now tftp.socket` starts the TFTP server only when a request arrives.

## SSH (Secure Shell)

**SSH** gives you a secure remote command line. Everything, including the password, is **encrypted**.

| Fact | Detail |
|---|---|
| Port | **22** |
| Server | `sshd`, installed and running by default on RHEL |
| Configuration | `/etc/ssh/sshd_config` (the **server**), `/etc/ssh/ssh_config` (the **client**) |
| Encryption | Public-key cryptography to agree on session keys |

### Connecting

```bash
ssh 192.168.56.10                 # as your current user name
ssh ahmad@192.168.56.10           # as another user
ssh -l ahmad 192.168.56.10        # the same
ssh -p 2222 ahmad@server1         # a non-standard port
```

Names work through DNS or `/etc/hosts`. From Windows, use the built-in `ssh` command, **PuTTY** or **MobaXterm**.

How does `ssh` know to use port 22? `/etc/services` maps the name to the port (`ssh 22/tcp`). Your side of the connection uses a random **unprivileged source port** (1024 to 65535). This works the same way for every service.

### Hardening sshd

Edit `/etc/ssh/sshd_config` (or, on RHEL 9, add a file in `/etc/ssh/sshd_config.d/`):

```text
PermitRootLogin no            # nobody logs in directly as root
PasswordAuthentication no     # keys only (set up keys first!)
Port 2222                     # optional: a non-standard port
```

Logging in directly as root over the network is dangerous: anyone who guesses the password owns the server. Log in as a normal user and use `sudo`. (RHEL 9's default, `prohibit-password`, already blocks root password logins.)

When changing the port, update SELinux and the firewall **before** restarting, or you lock yourself out:

```bash
semanage port -a -t ssh_port_t -p tcp 2222
firewall-cmd --permanent --add-port=2222/tcp && firewall-cmd --reload
sshd -t                       # test the configuration
systemctl reload sshd
```

Keep your current session open until a new login works.

### Passwordless Login with Keys

In organizations, servers trust each other with **key pairs** instead of passwords:

```bash
ssh-keygen -t ed25519                     # creates ~/.ssh/id_ed25519 (private) and .pub (public)
ssh-copy-id ahmad@192.168.56.10           # appends the public key to the server's ~/.ssh/authorized_keys
ssh ahmad@192.168.56.10                   # no password asked
```

The **private key** never leaves your machine; protect it with a passphrase. The server only holds the **public** key.

### Copying Files over SSH

```bash
scp file.txt ahmad@server1:/tmp/                # copy a file
scp -r project/ ahmad@server1:/opt/             # a directory
sftp ahmad@server1                              # interactive transfer: get, put, ls
rsync -avz /data/ ahmad@server1:/backup/data/   # efficient sync (RHEL Fundamentals topic 11)
```

## Questions

1. After setting `Port 2222` and restarting sshd, nobody can connect. Name two things that were probably missed.
2. Why disable `PasswordAuthentication` once keys work?

<details>
<summary>Answers</summary>

1. The SELinux port label (`semanage port -a -t ssh_port_t -p tcp 2222`) and the firewall rule for 2222/tcp.
2. It stops password-guessing (brute-force) attacks completely: only holders of an authorized private key can log in.
</details>
